# 让一个人格活着，一天要花多少钱

> 这一页都是真实账单上的数字（人民币），和把数字降下来的四个改法。
> 结论先说：**贵的不是她说话，是系统替她"想"了不该想的事。**

---

## 一、基准

一天 24 轮对话（她主动 3~5 条），账单约 **¥1.5**。

对比：同一天里一个跑失控的 DSH 会话，单会话 **¥7.63**（1098 次调用）。

也就是说 —— **人格本身的成本很低，成本失控基本都来自工程问题。**

---

## 二、每轮 90K prompt 是怎么来的

第一次跑的时候，每次请求的输入是 84K~104K token，而她的对话只有几十个字。

拆开看：

| 组成 | 量级 |
|---|---|
| 工具定义（610 个，全部内联） | ~85K token |
| 人格 + 记忆 + 当前状态（bootstrap 文件） | 6~10K token |
| 对话历史 | 剩余 |

**根因：工具太多了。** 每个 MCP / 插件注册的工具都带着完整 JSON Schema 塞进 system prompt，
610 个工具就是 85K token —— 而一次对话最多用到两三个。

## 三、四个改法

### ① 工具搜索（最有效）

不要把全部工具塞进 prompt，只给"搜索工具"这一个出口，用到再取：

```json
{ "toolSearch": { "enabled": true, "mode": "tools" } }
```

610 → **288** 个工具，prompt 直接砍掉一大块。
代价：多一次工具搜索往返，对闲聊场景无所谓。

### ② 缓存前缀：会变的字段放最后

DeepSeek 的上下文缓存按**前缀**命中。
我们的 bootstrap 文件里原本每分钟都在变（当前时间、感官计数、"你今天说话的样子"），
结果是：**每一步都要重新算前缀，缓存几乎全 miss**。

真实数据：一次 run 的第一步 `cacheRead` 只有 3K~16K，而后面几步能到 99K。

改法：

```
不变的（人格、记忆、长期状态）  →  前面
每轮都变的（时间、计数、心情）  →  最后
```

顺序一换，同一段内容就能复用缓存。

### ③ 静默 = 已处理，不是没处理

这是最贵的一个 bug。

她的空间评论 hook 有三种结果：回复 / 不回（`disposition: silent`）/ 失败。
旧代码把"不回"当成"没拿到回复文本"，于是**不记录已处理** ——

```
每 2 分钟 → 同一批评论 → 重新跑一次完整 agent（90K prompt）
一晚上 → 17 条任务 / 31 次调用
```

修法：

```js
if (disposition === "silent") {
  replied.add(item.key);      // 她选择不回，就是处理完了
  continue;
}
```

外加一个 10 分钟的尝试节流（失败才重试，成功和沉默都记账）。

**教训：任何"她决定不做"的分支，都必须落成"已处理"。**

### ④ 单轮步数要有上限

长任务（爬数据、改代码）放在同一个会话里，单轮能跑到 170 步。
一步 90K，170 步就是一场事故。

- 给会话设单轮步数上限
- 长任务拆到新会话
- 定时任务不要共用长会话的上下文

| 时段 | 内容 | 花费 |

| 00-03 | 两个长会话在跑 | ¥6.3 |

**她的部分（非 DSH 残差）当天是 ¥1.50。**

## 五、怎么查

账单不用猜，几个地方都有：

- `~/.dsh/.dshw-usage.json` —— 今日用量、余额
- `~/.dsh/storages/cost-meter/ledger.json` —— 按天、按会话的 calls / cost
- 每个 run 的 `model.completed` 事件 —— input / cacheRead / output

**先看"谁在跑"，再看"跑了多少步"，最后才看"是不是模型太贵"。**
顺序反了，会去优化根本不存在的问题。
