# 踩过的坑（都会让角色"人格崩掉"）

> 这几条都不是提示词能修的。它们的共同点是：**你从聊天记录里看不出来，只有真聊才发现。**

---

## 坑 1：会话分裂 —— 她不承认自己说过的话

### 症状

```
她（主动）：我感觉要死了
你：咋了
她：我没咋啊，你这一惊一乍的
你：？？ 那你说自己要死了
她：我啥时候说要死了，你做梦呢吧
```

**她不是嘴硬，她真的以为自己没说过。**

### 原因

主动消息、连发补句、未回复跟进 —— 这些"她自己发起"的消息，如果走了**独立的会话**，她说完就扔了。

你回复时走的是主会话，主会话里根本没有那句话。

我们查出来的分布：

```
[会话A] 我感觉要死了          ← 主动消息
[主会话] 我没咋啊             ← 你回她
[会话B] 你睡了吗 三点半了
[会话C] 鼻子还堵着 睡不着
[会话D] 药吃了没
```

**一整段对话，其实是五个互不相通的对话。**

### 修法

所有"她主动说"的路径，都必须落到**同一个会话**：

```js
// ❌ 每条主动消息开一个新会话
sessionKey: "proactive:" + slot + ":" + date

// ✅ 用主会话
sessionKey: "agent:main:main"
```

### 代价

主动消息的"提示词"（比如「你刚上完第三节课」）会留在对话历史里。

**这个取舍值得** —— 记忆连续比提示词干净重要一百倍。

## 坑 2：`Attachment:` 和 `MEDIA:` 不是一回事

### 症状

发出去的表情包变成一段文字：

```
?
Attachment: C:\Users\...\05_wenhao.png
```

用户看到的是路径，不是图片。

### 原因

`Attachment:` 是**入站**格式（用户发给 agent 时，附件怎么表示）。

**出站（agent 发给用户）要用 `MEDIA:`。**

而且格式极严：

```
✅ 正确
快睡

MEDIA:C:\path\to\sticker.png

❌ 挤在一行
快睡 MEDIA:C:\path\to\sticker.png

❌ 加粗
**MEDIA:**C:\path\to\sticker.png

❌ 写在代码块里
\`\`\`
MEDIA:C:\path\x.png
\`\`\`
```

### 更麻烦的：它会自我复制

历史上的错误写法会**变成模型的先例**，它会照着抄。

我们改成 `MEDIA:` 之后，模型还是写 `Attachment:` —— 因为对话历史里全是旧的错误示范。

**改语法的时候，必须连历史记录一起清。**

## 坑 3：推理模型把思考过程发出来

### 症状

```
她：Wait — his sequence at 01:41 "在吗", then me at 01:42 "在"... 
    He was just checking if I'm there. As Dong Xiaohan at 1:42 AM...
    嗯，躺着呢，你干啥呢
```

英文思维链混进正文，而且一次要 **97 秒**。

### 原因

DeepSeek V4 / Kimi K3 这类是**推理模型**。如果请求里没正确关闭思考：

- 思考 token 会吃掉输出预算 → 空回复
- 或者思考内容直接混进正文

### 修法

**聊天场景优先用非推理模型。** 需要推理模型时，必须显式关掉：

```json
{ "model": "deepseek-flash", "thinking": { "type": "disabled" } }
```

或者按框架的方式设置 thinking 档位（不同框架参数名不同，要查）。

### 判断标准

跑完一轮之后看：

- 有**空回复** → 推理吃掉了预算
- 回复里出现**成段的英文** → 思考泄漏了

**两个都是推理模型的典型症状，不是提示词问题。**

## 坑 4：审计用的会话会污染下一次审计

### 症状

审计做了两轮，第二轮结果好得可疑 —— 因为它**在抄自己第一轮的答案**。

### 原因

模型的"先例效应"：它会跟自己前面说过的话保持一致。

如果审计工具每次用同一个 session，第二轮看到的上下文里有第一轮的输出。

**这跟"我是 Kimi"那个坑是同一个机制。**

### 修法

每次审计用**全新的会话**：

```js
const SESSION = "agent:main:audit-" + Date.now();   // 每次不同
```

### 同一个机制的另外两个表现

1. **角色承认自己是 AI** —— 因为历史里真的有三次「我是 Kimi」。**改提示词没用，要改历史记录。**
2. **错误格式自我复制** —— 见坑 2。

**记住这条：模型跟着先例走，不是跟着规则走。**

## 坑 5：数据库是 WAL 模式，只读连接看不到新数据

### 症状

你查数据库，看到的是一小时前的状态。后台明明已经写进去了。

### 原因

SQLite 的 WAL 模式：新数据先写进 `-wal` 文件，稍后才合并进主库。

**只读连接可能读不到 WAL。**

### 修法

诊断脚本别用只读模式：

```js
// ❌
new DatabaseSync(path, { readOnly: true })

// ✅
new DatabaseSync(path)
```

## 坑 6：插件里的工具代码是死的

### 症状

「AI 说它没有这个工具」「搜不到」「这个能力没给我开」。

### 原因

某个第三方插件自带完整的 `tools.js`，但**入口文件从来没调用注册函数**。

我们在 `index.js` 顶部找到一行注释，写着：

```
不注册 Agent 工具，避免重复实现；Agent 回复时由 deliver 自动发送
```

**于是整个文件都是死代码。**

### 修法

```js
import { registerTools } from "./tools.js";
...
api.registerChannel({ plugin: ... });
registerTools(api);   // 加这一行
```

### 教训

**别信插件的 README，看入口文件。** 文档里写的功能可能一行都没接上。

## 坑 7：注册工具被静默拒绝

### 症状

`api.registerTool` 不抛错、日志里没有失败、但 AI 就是看不到工具。

### 原因

OpenClaw 要求插件在 manifest 里**先声明**它要注册哪些工具：

```json
// openclaw.plugin.json
{
  "contracts": {
    "tools": ["tool_a", "tool_b"]
  }
}
```

不声明的话，注册会被拒绝，**而且只写一行警告**：

```
[plugins] plugin must declare contracts.tools before registering agent tools
```

### 修法

声明 + 重启。重启后那行警告消失，就说明生效了。

### 教训

**"注册没报错"不等于"注册成功"。** 要查网关日志里的 `[plugins]` 警告。

## 坑 8：把「搜索返回空」当成「工具不存在」

### 症状

AI 说"我没有这个工具"、"这个能力没给我开"。我拿 hook 测了五轮，全说没有，
**于是花两个小时去修本来没坏的东西。**

### 原因（两个叠加，很容易互相掩盖）

**一、`tool_search` 返回空 ≠ 工具不存在。**

我曾把 `tools.toolSearch` 关掉（让工具直接进提示词），目录就空了 ——
此时 AI 去"搜"工具，永远得到 `[]`，它会诚实地报告"没有"。

**二、只看"搜索"这一条路。**

搜索是工具发现的**一种**方式，不是唯一方式。工具可能就在提示词里，
AI 只是没想到去调，或者它先搜了一下、搜空了、就放弃了。

### 修法

1. **先在日志里确认注册成功**
   ```
   [local-tool] OK onebot_post_qzone
   ```
   注册成功但 AI 说没有 → 问题不在注册。

2. **让 AI 直接调，别让它搜**
   人格里写清楚：`你有 onebot_post_qzone 这个工具，直接调，不要用 tool_search 找。`

3. **实测**：用 `POST /hooks/agent` 触发一次"调用 xxx 工具"，
   看返回里有没有 `toolResult`。**hook 回合里工具是完全可用的** ——
   （我们后来实测确认：hook 触发的回合里，AI 成功调用了插件工具并发了语音条）

### 教训

**「搜不到」和「不存在」是两件完全不同的事。**

我当时把这两件事混成一件，写下了错误的结论（"hook 回合工具受限"），
还把它当成通用规律去排查别的故障 —— **一个错误的诊断，会浪费后面所有的时间。**

## 坑 9：连续重启网关 = 制造僵尸

### 症状

网关端口在监听、TCP 能连，但 HTTP 永远超时；日志里出现：

```
Another gateway (pid XXXX) already owns this state directory
Gateway process is running but port 18789 is still free
Gateway service is still starting after 90s
```

### 原因

**网关启动要 3~5 分钟**（数据库校验、schema preflight、通道初始化）。

如果你在这期间又点了一次重启：

1. 新的实例起来抢状态目录
2. **旧实例仍然占着 SQLite**（29 MB 的库写入很慢）
3. 多个实例互相锁，全部卡死

### 修法

```powershell
# 1. 停
openclaw gateway stop
# 2. 杀掉残留 node（保留你自己的守护进程）
Get-CimInstance Win32_Process -Filter "Name='node.exe'" | ... Stop-Process
# 3. 只起一个
schtasks /run /tn "OpenClaw Gateway"
# 4. 等 5 分钟，别碰
```

### 教训

**重启不是"点一下就好"，是一次 5 分钟的操作。** 中途再点，等于把系统搞崩。

## 坑 10：补句机制写死了渠道

### 症状

在 QQ 上聊天，**微信里却收到她的回复**。

### 原因

"连发补句"的脚本里把渠道和收件人写死成微信：

```js
channel: "openclaw-weixin", to: "<微信 id>"
```

它监视的是**主会话**，看见新消息就补——不管这条消息是从哪个渠道来的。

于是 QQ 上的对话，补句全跑到微信去了。

### 修法

**补句要跟着会话当前的渠道走**：

```js
function currentRoute() {
  const e = JSON.parse(sessionEntry);
  const r = e.delivery.route;
  return { channel: r.channel, to: r.target.to, accountId: r.accountId };
}
```

### 教训

**任何"她主动发消息"的路径，都要读当前路由，不能写死。** 一旦多通道，写死的地方全是雷。

## 坑 11：控制标记漏进了正文

### 症状

她突然发来一句：

```
NO_REPLY
```

或者 `[[表情包:无语]]` 原样出现在聊天框里。

### 原因

发送层和"决定要不要回"的判定层**共用了一段模型输出**。

- "要不要回"靠模型输出哨兵文本 `NO_REPLY` 来判断
- 但那个哨兵是**文本**，只要有一条路径没过滤，就被当成正文发了出去

我们一天里漏了 3 次。

### 修法

两层都要堵：

```js
// 1) 输出侧：任何控制标记都进黑名单
const CONTROL = /^(NO_REPLY|SILENT|SKIP|\s*)$/i;
if (CONTROL.test(text)) return;      // 不发，也不进历史

// 2) 判定侧：用结构化结果，不要用哨兵文本
{ disposition: "silent" }   // 模型直接说"不回"，而不是输出一个暗号
```

`[[…]]` 这类动作标记同理：**发送前必须过一遍标记解析**，
解析残留的（写错的标记）宁可当普通文字删掉，不能原样发给用户。

### 教训

**哨兵文本是给代码看的，不是给人看的。**
只要它有机会走进用户的聊天框，就迟早会走进去。

## 坑 12：把"她选择不回"当成"没回复"

### 症状

账单里出现一条每 2 分钟一次、每次 90K prompt 的固定开销，
而她其实一晚上都没说话。

### 原因

评论检查脚本有三种结果：回了 / 不回 / 失败。
代码判断的是"有没有回复文本"，于是：

```
没文本 → 以为失败 → 不标记已处理 → 下一轮同一个评论再跑一次
```

**"不回"是一个合法结果，不是错误。**

### 修法

```js
if (disposition === "silent") {
  handled.add(item.key);   // 她选择不回 = 处理完了
  continue;
}
if (failed) continue;      // 失败才留给下一轮
```

外加 10 分钟尝试节流，避免"失败-重试"风暴。

### 教训

**所有会花钱的轮询，必须对"没有输出"这件事有明确语义。**
没有语义 = 无限重试。

## 一条通用经验

> **所有"她说了但否认"、"她重复发同一句"、"她突然变英文"这类问题，
> 九成不是提示词，是数据流。**

先看**她实际收到了什么上下文**，再改人格。

改人格是最后一步，不是第一步。
