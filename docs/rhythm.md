# 消息节奏：为什么你的 AI「哪里不对」

> 大部分人格工程只调"怎么说"（用词、标点、句长）。
> 还有一件同样明显、但几乎没人量的东西：**她一次说几句。**

---

## 一、数据

从 1 份 5000 条的真实聊天记录里量出来的：

| 指标 | 真人 |
|---|---|
| 每回合平均**条数** | **1.99** |
| 每回合平均**字数** | **14.1** |
| 每条平均字数 | 7.1 |
| **连发 2 条以上的回合** | **47.6%** |

分布（可以直接抄进概率表）：

```
1 条   52.4%
2 条   24.3%
3 条   11.2%
4 条    6.4%
5 条    2.6%
6 条    1.0%
```

## 二、这个数字为什么重要

AI 默认**每回合回一条**。

于是你看到的差别是：

```
真人：  好无聊         ← 3 秒后
        你在干嘛       ← 又 2 秒后
        回我 快点

AI：    好无聊 你在干嘛 回我快点      ← 一条说完
```

用词完全一样，但读起来就是"不像"。而且**你调提示词永远修不好这个** ——
因为问题不在文本里，在**消息条数**里。

## 三、更隐蔽的一个坑：别只盯单条长短

很多人发现"话太多"就去压单条长度，结果做过头：

```
每条都 5 个字 → 看起来很像我 → 但一个回合只说 5 个字
```

真人每回合说 **14 个字**，分散在 2 条里。

**标尺应该是"每回合总字数"，不是"每条字数"。**

这也是为什么单靠压短句做不像 —— 你把总字数也压掉了一半。

## 五、怎么实现连发

核心矛盾：**大多数聊天框架是"一问一答"，没有"一次多条"的概念。**

### 方案 A：发送层拆条

如果你的框架支持一条回复拆成多条发送，直接用。最干净。

### 方案 B：补句（我们用的）

一个常驻监视器盯着对话：

```
她回了一句
   ↓
监视器发现 → 按真实分布掷骰子
   ├─ 52.4%  不补
   ├─ 24.3%  补一句
   ├─ 11.2%  补两句
   └─ ...
   ↓
补之前先看他回没回 —— 回了就取消
```

参考实现：`scripts/burst-watcher.mjs`

## 六、时序才是成败关键（我们踩的坑）

第一版我们把补句间隔设成 **3~12 秒**。

结果：**用户以为她说完了，刚回一句，她的补句就到了。**

看起来像在无视你。

### 正确做法

```
间隔        0.2 ~ 0.9 秒     ← 几乎立刻
轮询        0.8 秒           ← 别用 3 秒，太迟钝
前置检查    每次发射前都查   ← 他回了就不补
```

实测：

```
她第一条发出 → 补句送达 = 3.5 秒
其中 3 秒是模型生成，0.9 秒是等待
```

**3.5 秒是极限了。** 真人打字也就 2~3 秒。

### 剩下的窗口

如果你在她发完后 3.5 秒内回复，补句还是会落在你后面 —— 因为那时消息已经在生成路上了，拦不住。

**这个窗口没法根除，只能压小。** 压到 3.5 秒后，正常打字速度下基本感觉不到。

## 七、还有一个更隐蔽的

连发要能"判断该不该补"。三个硬条件：

1. **她刚发的是表情包 / 纯问号** → 不补（没东西可加）
2. **他刚回过** → 不补（会显得像无视他）
3. **她输出 NO_REPLY** → 停止整轮补句

少了任何一条，都会出现"她连着发三张一样的表情包"这种事。

## 八、别把连发做成定时任务

我们试过用定时任务做连发，失败了。

原因：定时任务的最小粒度是分钟，而连发需要**秒级**响应。

必须是常驻进程。
